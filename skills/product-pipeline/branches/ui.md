# ui branch

Load for the actual ui task. Use the [common execution contract](../README.md#common-execution-contract); this file grants no action authority.

## Trigger and input

A screen/component needs typography, layout, focus or visual polish.
Input: Chosen journey, actual content/data limits, platform, design tokens and contextual taste examples.

## Procedure and composition

Choose a coherent visual language suited to this product. Inspect hierarchy, spacing, text, contrast, focus, targets and motion. Render real containers and stress long/empty/localized content and each state. Motion conveys causality, respects reduced motion and remains interruptible.
Optional complement: Emil/design guidelines for craft; platform/framework methods only where relevant. Verify installation, provenance and its narrower contract before loading. Do not import an external body merely because this branch names it.

## Output and proof

Implemented or reviewable interface plus actual rendered state evidence.
Next context: QA after rendering and state coverage; UX if structure, not styling, is the bottleneck. Record source/entity revision, falsifier, uncertainty and named receiving owner; require actual acknowledgment/consumption before claiming handoff. See the [source catalog](../SOURCES.md) for conceptual credits, not efficacy evidence.

## Silence and recovery

A screenshot is not usability or conversion proof. Avoid generated filler, uniform templates and unsolicited direction resets.
Keep a known-good baseline; isolate regressions to state, container or data boundary before further polish.
Duplicate/stale events, unavailable capacity/consumer, immature windows or a missing grant select no-op, bounded observation or explicit defer. A routing offer proves none of execution, recovery, operator-time savings or business impact.
