# retention branch

Load for the actual retention task. Use the [common execution contract](../README.md#common-execution-contract); this file grants no action authority.

## Trigger and input

Support/cancellation/recurring-use evidence warrants review.
Input: Eligible mature cohorts, complaints, support records, product cadence and consent/privacy limits.

## Procedure and composition

Distinguish voluntary habit/value, bugs, support debt and billing confusion. Segment evidence without inventing loyalty. Design bounded recovery with a clear exit; include support operations, cancellation, data export/deletion and service reliability where relevant. Immature cohorts remain inconclusive.
Optional complement: churn/support/billing/reliability methods for the observed cause. Verify installation, provenance and its narrower contract before loading. Do not import an external body merely because this branch names it.

## Output and proof

Retention/support problem brief and a falsifiable recovery or reliability proposal.
Next context: experiment for behavior hypotheses; QA/delivery for proved defects. Record source/entity revision, falsifier, uncertainty and named receiving owner; require actual acknowledgment/consumption before claiming handoff. See the [source catalog](../SOURCES.md) for conceptual credits, not efficacy evidence.

## Silence and recovery

Do not hide cancellation, delete data, send recovery messages or duplicate refunds without exact current authority.
Persist customer operation IDs and ownership; reconcile ambiguous recovery effects before retry; escalate service incidents through existing owners.
Duplicate/stale events, unavailable capacity/consumer, immature windows or a missing grant select no-op, bounded observation or explicit defer. A routing offer proves none of execution, recovery, operator-time savings or business impact.
